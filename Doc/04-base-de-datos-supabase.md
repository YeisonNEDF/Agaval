# 04. Base de datos y Supabase

## Adaptación del enunciado

El documento propone SQL Server, pero la implementación usa PostgreSQL 17-compatible mediante Npgsql para ejecutarse en Supabase. Clean Architecture permite cambiar el adaptador sin modificar Domain o Application.

Equivalencias principales:

| SQL Server | PostgreSQL/Supabase |
|---|---|
| `INT IDENTITY` | `integer GENERATED BY DEFAULT AS IDENTITY` |
| `NVARCHAR(n)` | `character varying(n)` |
| `BIT` | `boolean` |
| `DECIMAL(10,2)` | `numeric(10,2)` |
| `DATETIME2` | `timestamp with time zone` en UTC |
| `GETDATE()` | `CURRENT_TIMESTAMP` |

Se conservan tablas y columnas en español, claves foráneas, defaults y checks.

## Qué dato se necesita

Se requiere la **cadena de conexión PostgreSQL**, no la URL pública del proyecto ni una anon key. El formato esperado es:

```text
Host=HOST;Port=5432;Database=postgres;Username=USUARIO;Password=CLAVE;SSL Mode=Require;Trust Server Certificate=true
```

Supabase muestra esta información en **Project settings > Database > Connection string**.

## Pooler recomendado

- Para `dotnet ef database update`: conexión directa o pooler en modo sesión.
- Para runtime serverless o muchas conexiones cortas: pooler según el patrón de despliegue.
- El pooler en modo transacción no es apropiado para todos los flujos de migración y sesión de EF.

## Configuración segura

Local:

```bash
export ConnectionStrings__Database='CADENA_COMPLETA'
```

Docker Compose:

```bash
cp .env.example .env
# editar AGAVAL_DATABASE_CONNECTION
```

Kubernetes:

```bash
kubectl create secret generic agaval-secrets \
  --from-literal=database-connection='CADENA_COMPLETA'
```

`infra/k8s/secret.example.yaml` es solo una guía y no debe recibir la clave real.

## Aplicar migraciones

```bash
cd backend
dotnet tool restore
dotnet ef database update \
  --project src/Agaval.Inventory.Infrastructure \
  --startup-project src/Agaval.Inventory.Api
```

Para inspección o ejecución SQL controlada también existe `backend/database/initial.sql`.

## Seeds

La migración incluye:

- Electrónica, Oficina y Aseo como categorías activas.
- dos productos de ejemplo para que el dashboard no inicie vacío.

Los identificadores del seed son estables dentro de la migración y las claves identity continúan su secuencia normalmente.

## Política de migración en producción

`Database:ApplyMigrationsOnStartup` está desactivado por defecto. En una aplicación con varias réplicas, el pipeline de release debe ejecutar las migraciones una sola vez antes de actualizar los Deployments. Esto evita carreras entre pods y desacopla un cambio de esquema de la disponibilidad del proceso web.

## Recuperación y seguridad

- No registrar cadenas de conexión ni respuestas que contengan credenciales.
- Rotar la contraseña si se expone.
- Usar backups/PITR de Supabase según el plan contratado.
- Probar migraciones y rollback de aplicación en un proyecto de staging.
- No ejecutar un downgrade destructivo sin respaldo y ventana de mantenimiento.
